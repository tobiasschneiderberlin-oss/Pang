Chapter five · Motion

Springs by default.
Tweens by exception.

GATES → P15, P16
LIB → src/lib/motion/presets.ts
VIEW TRANSITIONS → ARRIVAL · DETAIL

Motion One presets live at src/lib/motion/presets.ts. A component that writes its own duration: fails the lint gate. Arrival and detail navigation use the native View Transitions API — not Framer Motion.

Spring · roomEnter

Warm overshoot.

stiffness 170 · damping 26 · mass 1. Arrival of the Room. A touch of overshoot — like a painting settling on its hook.

Tween · arrivalLamp (exception)

Load-bearing linearity.

cubic-bezier(0.4, 0, 0.2, 1) · 300ms. The only sanctioned tween. Used when timing must be predictable — the lamp crossfade.

View Transitions

Cross-document. Arrival chapter. Detail zoom. Detail-to-detail navigation.

Reduced motion

Every preset ships with a reduced-motion variant — fades replace slides. Enforced by P23.

Tonal breath

A one-beat hold. Silence as information when streaming throughput drops below 5 tokens / second.

Appendix E — First-boot checklist.
TIME → 20 MIN
OUTPUT → PASSES P1
AUDIENCE → CLAUDE CODE

The sequence a clean checkout should run through on day zero. At the end of step 09, pnpm ci passes all 47 gates on an empty app. Everything else is feature work.

  1. Scaffold the repo layout from Appendix D.

    Create every directory listed in the tree, empty. Gates reference paths by name — if the folder does not exist, the linter cannot run. This is the only step that is manual; the rest are pnpm tasks.

    pnpm dlx create-pang . --template 2026

  2. Write src/styles/tokens.css from Appendix A.1.

    Copy the CSS block verbatim. Do not edit values without a doctrine edit. tokens-lint.ts reads this file as the authority — if a property is renamed here, every token site auto-fixes.

  3. Register the 9 knobs as @property.

    In src/styles/globals.css, declare each knob with @property so it participates in animation and interpolation. This is what lets --knob-time-warmth breathe across the Room.

    pnpm run knobs:register

  4. Install .pang/gates.yaml.

    Drop Appendix B into a machine-readable YAML file. Pre-commit hook + CI both read it. No gate runs independently — they are all declared in one place.

    pnpm run gates:install

  5. Wire CI — Lighthouse, axe, tokens, vitals, eval.

    GitHub Actions from .pang/ci/. Every PR runs on mid-tier Moto G throttle for P1 and P7. Desktop runs are informational only; the floor is mobile.

    pnpm run ci:local # preview the run

  6. Mount the Room at app/page.tsx.

    The home route imports <Room /> and nothing else. No hero, no onboarding, no nav bar. The first surface a user sees is the collection.

  7. Wire passkeys + magic link.

    Auth ships enabled at boot — no password field can enter the repo (gate P10 will refuse the commit). Magic link is for first sign-in on a new device; passkey is the default.

    pnpm run auth:init

  8. Seed the voice in src/ai/prompts/voice.xml.

    The ten lines from Chapter 01 go verbatim into the voice seed. Every user-facing agent's system prompt imports this file — A4 refuses prompts that do not.

  9. Run pnpm ci and confirm all 47 gates pass on an empty app.

    If any gate fails at boot, the scaffold is wrong — fix the scaffold, never loosen the gate. A boot that skips a gate becomes a PR that skips a gate.

    pnpm ci
Appendix F — Doctrine edit protocol.
AUTHORITY → HUMAN
FILE → .pang/doctrine.md
CADENCE → MONTHLY REVIEW

This document is living but not loose. Adding a knob, removing a gate, introducing a component, changing a token — all are doctrine edits. They follow a fixed protocol so the system does not drift.

What counts as a doctrine edit

If the change affects what passes CI on an empty app, it is a doctrine edit and follows this protocol. If it is a feature inside an existing component with no new token, it is ordinary work.

  • Adding or removing a gate
  • Adding, renaming, or changing the range of a knob
  • Introducing a new component to Appendix C
  • Adding a new top-level folder in Appendix D
  • Changing a token value in Appendix A
  • Changing a voice rule, banned vocab list, or AI primitive

Where the doctrine lives

Two mirrors, intentionally. One is human, one is machine. Both move together in the same commit.

  • PANG_DS.html — this document, the editorial source
  • .pang/doctrine.md — extracted appendices, markdown, CI-readable
  • .pang/gates.yaml — the 47, structured
  • src/styles/tokens.css — the tokens, canonical values
  • CLAUDE.md — the two-page summary Claude Code loads first

The protocol

A doctrine edit is a single PR touching all five mirrors. Reviewed by one of the stewards. No partial landings.

  • 01 — Open a PR titled doctrine: <change>
  • 02 — Update PANG_DS.html prose first
  • 03 — Mirror into .pang/doctrine.md and gates.yaml
  • 04 — Land the code change in the same PR
  • 05 — Name what was replaced — gates and knobs are never removed silently
  • 06 — Bump PANG_DS version in the masthead

When code and doctrine disagree

The code wins. Always. A mismatch is not ambiguity — it is a bug in the doctrine, and the doctrine is updated the same day. This inverts the usual relationship; it is deliberate.

  • The code is what ships; the doctrine describes what ships
  • A doctrine that contradicts the code mis-guides Claude Code
  • Same-day correction is a gate, not a norm
  • Stewards rotate quarterly; no one owns the doctrine alone
§ The signing clause
PANG ships under this doctrine. A commit that cannot cite a gate, a token, a knob, a component, or a chapter of this document is a commit that has not arrived yet. The system holds because the rules are small, named, and the same for every pull request.
