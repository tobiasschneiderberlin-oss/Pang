# Tech-Debt + Cleanup Audit — Pre-Backend

**Date:** 2026-04-28
**Status:** Reference document for the iter-23b reset.

The framing isn't "what hurts to maintain" (the new app is too small for that). It's:

> **"Given a clean break from the old approach, what do we delete, what do we harvest before deleting, and what foundations do we lay before the backend locks them in?"**

That's a triage audit, not a debt-impact-effort matrix.

---

## The honest answer

**Yes, now is exactly the right moment** — but the work splits three ways, not the typical one:

| Bucket | What it is | Why now |
|---|---|---|
| **Delete** | Old PANG codebase, doctrine, archived assets | Cheap to remove while you still remember why; 705 MB and 261 TS files of cognitive overhead |
| **Harvest** | ~1,400 lines of *genuinely* good auth code in old PANG | Gone forever the moment you delete; saves 1–2 weeks of backend work |
| **Foundation** | Things in the new app that will compound when backend lands | Cheaper to fix in 60 files than in 200 |

What you should **not** do is run a classic Impact-Risk-Effort grid on the new app. It's 60 files, six days old, and has no users. The "tech debt" framing implies accumulated cost from past decisions; this codebase hasn't accumulated anything yet. The relevant question is: *what foundation is missing that will cost much more after Supabase is wired in?*

## Bucket 3 — Foundation gaps in the new app

These are real and will compound badly with backend integration. Prioritized by cost-of-delay.

### Priority 1 — Do before any backend code (1–2 days)

| Gap | What's missing | Why it must come first |
|---|---|---|
| **No `.env` strategy** | No `.env.example`, no `process.env` boundary, no separation of `NEXT_PUBLIC_*` vs server-only | The first Supabase env variable will get pasted somewhere wrong without this. Vercel deploy will be guess-and-check. |
| **No error boundaries** | Zero `error.tsx` files in the app router | Every Supabase query is a future crash candidate. Add `app/error.tsx`, `app/(app)/error.tsx`, and per-route boundaries for camera/scan flows. |
| **No `lib/api/` boundary** | `lib/data.ts` is mock arrays imported directly from pages. Pages will become spaghetti the moment the data is async. | Define `lib/api/{artworks,artists,documents,auth}.ts` as the only place pages import data from. Mock now → real Supabase later → pages don't change. |
| **No service worker registration** | `manifest.json` exists but nothing handles install prompts, offline cache, or update flow | The whole PWA premise breaks without this. `next-pwa` or hand-rolled — pick one. |

### Priority 2 — Do alongside first backend wiring (2–3 days)

| Gap | What's missing | Why |
|---|---|---|
| **Zero tests** | No Vitest, no Playwright, no testing-library | Old app had Playwright + Vitest. Not pretending you'll backfill — but the auth flow and AI scan pipeline absolutely need contract tests before they ship. |
| **No CI** | No `.github/workflows/`, no pre-push hook | Right now you can ship type errors silently; you've already paid for that once. |
| **Route group is incomplete** | `app/(app)/` has only `collection/` and `patterns/`. Settings, add, artwork, documents, profile all sit at top-level | Decide: are these all behind auth? Then they all belong in `(app)/`. The current layout means the splash → onboarding → collection auth gate is implicit. Make it structural. |
| **No auth context** | No equivalent of `useUser()` or `<AuthProvider>` | Every page that needs the current user will re-fetch independently. Set the seam now, even with a mock. |

### Priority 3 — Defer until backend integration reveals shape (don't do now)

These are real but premature to refactor without seeing how the backend pulls on them:

- **Component organization** (22 flat components + 60 in `ui/`) — fine until 50+ business components
- **`hooks/` size** (5 hooks) — will grow naturally; refactor when patterns emerge
- **Inline styles vs CSS variables** — touched lightly in components like splash; not yet a problem
- **`touchstart` vs Pointer Events** — works; do one sweep before public launch
- **Multiple lockfiles** (`pnpm-lock.yaml` + my install briefly added `package-lock.json`) — already cleaned up
- **`localStorage` reliance** — fine for accent color, onboarding flag, analytics. Auth will move to Supabase cookies regardless.

## What "tech debt" looks like more honestly here

The classic debt formula `Priority = (Impact + Risk) × (6 − Effort)` is for established codebases. For this one, the more useful framing is **lock-in cost**: how much does deferring this fix multiply when the backend is in place?

| Item | Fix-it-now cost | Fix-it-later cost (after backend) | Multiplier |
|---|---|---|---|
| `.env` boundary | 1 hour | 1 day (rotate exposed keys, refactor every server component) | 8× |
| Error boundaries | 2 hours | 0.5 day per route (8 routes × ad hoc try/catch) | 4× |
| `lib/api/` seam | 4 hours | 2 days (refactor every page that imports `data.ts`) | 4× |
| Service worker | 1 day | 2 days (debug install bugs in production) | 2× |
| Tests + CI | 1 day for skeleton | 1 week for retroactive coverage | 5× |

The Priority 1 items have an 8–4× lock-in multiplier. Doing them now is the cheapest backend prep available.

## Concrete sequence

I'd run it as one focused 3-day pass, then stop:

**Day 1 — Salvage + delete**
- Tarball `.claude/worktrees/zen-greider-9753a7/` to off-machine storage
- Copy `signed-link.ts`, `invite.ts`, `rate-limit.ts`, `webauthn/*` into `b_3gmUyvQpair/lib/auth/` (with their `.test.ts` companions)
- Copy `src/ai/prompts/` skeleton into `b_3gmUyvQpair/lib/ai/`
- Delete old worktree, the 9 doctrine MDs, archived directories
- Commit

**Day 2 — Foundation in `b_3gmUyvQpair/`**
- Create `.env.example` + `lib/env.ts` (Zod-validated) for client + server env split
- Add `app/error.tsx`, `app/(app)/error.tsx`, `app/artwork/[id]/error.tsx`
- Refactor `lib/data.ts` → `lib/api/{artworks,artists,collectors,documents}.ts` keeping the same exports (still mock data; just behind the seam)
- Wire service worker registration (next-pwa or `serwist`)
- Move `add/`, `artwork/`, `documents/`, `settings/`, `profile/` into `app/(app)/`
- Commit

**Day 3 — Test + CI scaffolding**
- Vitest config + 3 starter tests (one per harvested auth file)
- Playwright config (lift from old PANG, replace specs with one smoke test)
- `.github/workflows/ci.yml`: typecheck + tests on every PR
- Pre-push hook: `npm run typecheck && npm run test`
- Commit

**Day 4+: backend integration begins.** From here forward, every Supabase call lives behind `lib/api/`, every error has a boundary, every env var is typed, and the auth machinery has its bones already laid.
